# ADR-007: `usernameAndPassword` em vez de `email` para autenticação da operadora

**Data:** 2026-05-22
**Card:** VS01
**Status:** Aceito

## Contexto

O RF01 do PRD descreve o login da operadora como "e-mail e senha". O Wasp 0.22
oferece dois métodos nativos de autenticação aplicáveis:

- `usernameAndPassword` — um campo `username` (string livre) + senha.
- `email` — um campo `email` validado, com **fluxo de verificação por e-mail**
  e **reset de senha por e-mail** obrigatórios. Exige `app.emailSender(...)` e
  páginas cliente para `/email-verification` e `/password-reset`.

A operadora é única, criada via seed (RF01: "Não há auto-cadastro; conta criada
via seed ou painel admin"), e o sistema é auto-hospedado em servidor próprio do
teatro sem provedor de e-mail configurado nesta v1.

## Decisão

Adotar o método `usernameAndPassword` no VS01, armazenando o e-mail da operadora
no campo `username` (que é apenas uma string para o Wasp).

A UI do `/login` continua semanticamente correta: o input tem label "E-mail",
type `email` e autocomplete `username`, atendendo ao RF01 do ponto de vista do
usuário. A diferença é apenas backend — em `AuthIdentity`, `providerName` será
`"username"` e `providerUserId` será o e-mail em lowercase (normalização que o
próprio Wasp aplica em `createProviderId`).

## Motivo

O método `email` arrasta dependências fora do escopo do VS01:

1. **`emailSender`** — exige configurar um provedor (SMTP, SendGrid, etc.) ou o
   `Dummy` (que loga no console). Nenhum dos dois está alinhado com a v1
   auto-hospedada sem infraestrutura de e-mail (PRD §4 RNF05).
2. **`/email-verification`** — página cliente obrigatória para o fluxo de
   verificação. Como o cadastro é por seed, o titular **nunca recebe link** —
   o passo é supérfluo no nosso fluxo.
3. **`/password-reset`** — outra página obrigatória. Reset de senha da
   operadora hoje é trivial: editar o seed e re-executar (auto-hospedagem).
4. **Páginas extras = scope creep** — violaria a regra TDAD "mínimo para o
   teste passar" no VS01, já que nenhum critério de aceite as exercita.

Os "ganhos" do método `email` (validação de formato, verificação de
propriedade) são marginais para um único usuário interno e podem ser obtidos
no `usernameAndPassword` via UI (`type="email"`, validação no formulário).

## Alternativas consideradas

- **`email` com `emailSender: { provider: Dummy }` e páginas stub** —
  funcionaria, mas adiciona 2 rotas, 2 componentes, e configuração morta no
  `main.wasp.ts`. Custo > valor para v1.
- **Auth customizada (JWT/sessão manual)** — descartada de imediato pelo
  CLAUDE.md §3.1: "Autenticação é gerenciada pelo Wasp — nunca implementar JWT
  ou sessão manualmente".

## Consequências

### Positivas
- VS01 fecha com superfície mínima de auth (1 método, 0 dependências externas).
- Sem ramificação de fluxos: cadastro = seed, login = form, fim.
- Compatível com o PIA (ADR-006 e `docs/lgpd/PIA.md`): o CPF não é parte da
  identidade de auth, apenas dados de locatário (VS03).

### Negativas / a tratar adiante
- Não há fluxo de reset de senha do tipo "esqueci minha senha". Se a operadora
  esquecer, o atendimento é manual (re-seed). Aceitável para 1 usuário interno.
- Validação semântica de e-mail acontece apenas no cliente (atributo
  `type="email"` do input). O backend trata como string opaca.

### A reavaliar no Épico 4 (LGPD e Privacidade)
- Se for criado um portal de **self-service para o titular** (locatário), o
  método `email` do Wasp passa a fazer sentido — verificação de e-mail vira
  garantia de identidade legítima. Reavaliar nessa janela.

## Itens de implementação

- `main.wasp.ts`: `app.auth({ userEntity: "User", methods: { usernameAndPassword: {} }, onAuthFailedRedirectTo: "/login" })`
- `src/server/seeds/operadora.ts`: usa `createProviderId("username", email)` +
  `sanitizeAndSerializeProviderData<"username">({ hashedPassword })` +
  `createUser(providerId, providerData, {})`.
- `src/client/pages/LoginPage.tsx`: UI com label "E-mail" e `type="email"`,
  invoca `login({ username: email, password })` do `wasp/client/auth`.
- Testes E2E em `tests/e2e/vs01-login.spec.ts` validam o critério de aceite.
